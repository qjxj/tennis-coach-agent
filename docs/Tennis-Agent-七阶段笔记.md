## 2. 阶段一：Tool

### 目标
把姿态管线包成模型能调用的工具。

### 关键设计
| 设计 | 原因 |
|---|---|
| `Annotated[类型, "说明"]` | 参数说明进 schema（`:param` 风格不会被解析） |
| `Literal["lite","full"]` | 锁死枚举，杜绝 `"left_hand"` 这类乱填 |
| docstring 写"不适用" | 决定模型会不会误用 |
| 返回 JSON 字符串 | ToolMessage 是文本；避免 Python repr |
| 异常转 `build_err` | 可恢复失败，不打断链路 |

### 实测 schema
```
video_path   击球视频的相对路径...        enum=None
wrist        主手：auto 按可见度自动判断   enum=['auto','left','right']
model_size   姿态模型：lite/full          enum=['lite','full']
必填: ['video_path']
```

### 数字
- 单次分析 93 帧，耗时约 7~8 秒
- 输出 `confidence = 可用帧比例 × min(1, 事件数/3)`

### 面试 30 秒
> 工具的本质是 JSON Schema，模型看不到实现。所以我用 `Annotated` 写参数语义、`Literal` 锁枚举、docstring 写清"不适用场景"，返回统一的 `ToolResult` 带置信度和证据路径，让上层能做校验和拒答。

## 3. 阶段二：Loop

### 核心 8 行
```python
g = StateGraph(MessagesState)
g.add_node("model", model_node)
g.add_node("tools", ToolNode(TOOLS))
g.add_edge(START, "model")
g.add_conditional_edges("model", tools_condition)
g.add_edge("tools", "model")
app = g.compile()
```

### 四步循环
```
① 发 messages + tools(schema)
② 模型回 tool_calls（JSON，不执行代码）
③ ToolNode 解析 arguments 并执行
④ 结果作为 ToolMessage 回填 → 再发一次
```

### 三个易错点
1. `tool_call_id` 必须配对，否则模型会重复下单
2. `recursion_limit` 是兜底，防死循环
3. `bind_tools` 每轮都要带 schema（不存进 messages）

### 实测暴露的问题
模型看到 `confidence=0.559` 只说"仅供参考"，**仍然给了三条建议** → Prompt 是软约束，硬约束要进代码（阶段五）。

### 面试 30 秒
> Agent 和 workflow 的区别就在条件边：下一步由模型决定。模型只输出 JSON，执行是 ToolNode 做的；结果通过 ToolMessage 回填，`tool_call_id` 保证配对。

## 4. 阶段三：Context

### 两个手法
| 函数 | 作用 |
|---|---|
| `compact_tool_result` | 只留 summary + 偏离 2σ 的异常 + 证据路径 |
| `prune_history` | 较早工具结果折叠成一行 |

### 数字
| 场景 | 前 | 后 | 降幅 |
|---|---|---|---|
| 单次工具结果 | 1387 字符（≈924 token） | 752 字符（≈501 token） | 46% |
| 三轮对话历史 | 2976 字符 | 1276 字符 | 57% |

### 四条原则
1. 磁盘存全量，上下文给摘要
2. 只传异常，不传全部
3. 证据用路径引用，不复述内容
4. 历史只留最近一份原文

### 面试 30 秒
> 工具返回不能全塞给模型。完整指标落盘，只回填"摘要 + 异常 + 证据路径"，单次从 924 token 降到 501；多轮再折叠旧结果，三轮降 57%。关键是保留证据路径，压缩不能让结论不可回溯。

## 5. 阶段四：Multi-Agent

### 结构（星型）
```
主智能体（工具只有 task）
  ├─ task("技术分析师") → 子图 A [analyze_stroke]
  └─ task("装备顾问")   → 子图 B [filter_rackets]
```

### 实测路由
| 输入 | 调度 |
|---|---|
| 预算 + 水平 + 手肘 | 装备顾问 |
| 视频路径 + 正手 | 技术分析师 |
| "你好" | 不调度 |

### 三个认知
1. 子智能体 = 独立编译的子图，通过普通工具 invoke
2. 上下文天然隔离（各自 sys_prompt + tools）
3. 回传要做长度上限（本项目 1200 字符），否则子图输出占满主上下文

### 装备推荐的关键设计
**硬约束用代码，软偏好用打分**：
- 硬约束：预算 / 水平 / 重量 / 护肘友好 → 过滤
- 软偏好：控制 / 力量 / 旋转 → 0~1 打分并给出拆解

### 面试 30 秒
> 星型拓扑，两个子智能体各编译成子图，主智能体只持有一个 task 工具做路由。收益是上下文隔离和工具选择空间收敛；代价是结果二次转述会折损，所以设了回传长度上限，评测里也专门看路由和参数归一化。

## 6. 阶段五：可靠性

### 三档门禁
| 状态 | 条件 |
|---|---|
| `refuse` | 置信度 < 0.6 / 零事件 / 有效帧 < 0.5 / 工具失败 / 返回不可解析 |
| `warn` | 异常击球 ≥ 2 |
| `ok` | 其余 |

### 单测（6/6）
```
正常 → ok | 低置信 → refuse | 零事件 → refuse
有效帧低 → refuse | 工具失败 → refuse | 裸字符串 → refuse
```

### 抓到的真 Bug：沉默失败
```
model_size='full' → usable 0.022, events 0     ← 工具返回 ok=true, confidence=0.05
model_size='lite' → usable 0.559, events 3
```
把"管线坏了"伪装成"没击球"。修法：有效帧 < 10% 直接报错，并在错误信息里写"请改用 lite"，模型据此自动重试成功。

### 四条原则
1. 硬约束用代码，不用 Prompt
2. 失败要显式，不能伪装成正常结果
3. 错误信息要可操作（告诉模型下一步怎么做）
4. 先降级（换参数重试），再拒答

### 面试 30 秒
> 模型看到低置信度只会嘴上说"仅供参考"，照样给建议。所以把门禁做成代码：低于阈值直接拒答，返回确定性文案，模型无权绕过。另外发现模型选了不兼容权重导致检出率 2%，但工具返回的是"ok + 0 次击球"——沉默失败。改法是低检出率直接报错并给出替代参数，模型据此自愈。

## 7. 阶段六：评测

### 断言过程，不断言文本
```python
expect_dispatch      # 该调度谁
forbid               # 不该调度谁
expect_no_dispatch   # 闲聊/越界不该调度
expect_refuse        # 该拒答
must_contain(_any)   # 关键信息
expect_tool          # 子智能体里必须调用某个工具
forbid_tool          # 不该调用某个工具
turns                # 多轮，共用同一个 thread_id
```

### 两级断言（只有第一级是不够的）
```
主智能体层：调度了哪个子智能体        → expect_dispatch
子智能体层：里面到底调了哪个工具      → expect_tool
```
只断言第一层时，"它有没有真的去检索、真的去分析"是测不到的。

### 15 条用例 / 6 类
| 类型 | 数量 | 说明 |
|---|---|---|
| route | 6 | 该调度谁 |
| boundary | 2 | 越界与工具隔离 |
| gate | 1 | 该拒答 |
| scope | 2 | 闲聊/越界不该调度 |
| clarify | 1 | 缺参数先追问 |
| multi | 3 | 多轮，共用 thread_id |

### 结果
```
单轮 15/15
route 6/6 · boundary 2/2 · gate 1/1 · scope 2/2 · clarify 1/1 · multi 3/3
```

### 工具轨迹怎么采
子智能体的 `model_node` 在返回前把 `tool_calls` 追加到模块级列表，评测开始时 `begin_trace()` 打开。
用模块级列表而不是 `ContextVar`：LangGraph 可能在线程池里执行节点，`ContextVar` 不保证跨线程传播；
该开关只在评测（串行）里打开，服务端并发请求不记录，因此不存在互相串扰。

### 抓到的三个真 Bug
1. **门禁误伤装备顾问**：`evaluate()` 对所有工具生效，装备结果被当"零击球"拒掉。
   修法：按工具名 `analyze_stroke` 判断，而不是对所有 tool 消息生效。
2. **重复调度**：同一助手被调两次。修法：Prompt 增加"同一助手只调度一次"。
3. **单项被拒后整轮提前结束**：`stroke_vs_gear` 里视频被门禁拒掉之后，主智能体直接收尾，
   把"选球拍"那半句丢了。修法：Prompt 写明"某一项被拒只代表这一项做不了，其余仍要完成"。
   修完从 0/1 变成 4/5。

### 一条方法论更正
曾以为 `stroke_vs_gear` 是"波动"，实际是门禁 Bug 导致的**确定性失败**。
教训：**看起来不稳定，可能只是自己的 bug**；用 `--repeat` 区分"假波动"和"真 Bug"。

### 一个用例写法的坑
`stroke_vs_gear` 原来把视频路径写在"推荐球拍"那句后面，模型会误判路径属于哪个请求，
出现过"一个子智能体都不调度、24 秒直接作答"。
把路径挪到句首后抖动明显下降。教训：**评测用例的措辞本身也是被测系统的一部分**。

### 一个 harness 副作用
实测发现装备顾问会把 `filter_rackets` 连着调 4 次。加了 `MAX_TOOL_ROUNDS = 3`：
子智能体用满 3 轮工具后不再绑定工具，强制收尾作答。

### 成本
| 模式 | 耗时 |
|---|---|
| 单轮（15 条） | ~6 分钟 |
| 3 轮 | ~18 分钟 |

日常单轮冒烟，改 Prompt/代码后跑 3 轮。

### 面试 30 秒
> 15 条用例断言的是轨迹而不是文本，而且分两层：主智能体该调度谁、子智能体里实际调了哪个工具。它抓到三个真 Bug：门禁逻辑套用错对象、模型重复调度、以及单项被拒后整轮提前结束。还有一个反直觉的发现——同一条用例反复失败，最后查出来是我把视频路径写在了错误的从句后面，**评测用例的措辞本身也会影响结果**。

## 8. 阶段七：服务化

### 接口
```
POST /api/analyze      → {"status":"started","thread_id":"..."}
WS   /ws/{thread_id}   → dispatch / subagent_done / final / error
GET  /                 → 最小演示页
GET  /api/health       → 连接数
```

### 三个技术点
1. **同步编排丢线程**：`main_agent.stream()` 会阻塞事件循环
2. **线程→循环桥接**：`loop.call_soon_threadsafe(queue.put_nowait, ev)`
3. **保存任务引用**：`TASKS.add(task)` + `add_done_callback(TASKS.discard)`

### 实测
```
单会话：dispatch → subagent_done → final
并发：A-闲聊 events=['final'] / B-装备 events=['dispatch','subagent_done','final']
→ 两会话零串台
```

### 面试 30 秒
> 编排是同步阻塞的，必须丢到线程里，用 `call_soon_threadsafe` + `asyncio.Queue` 把事件搬回事件循环再广播。连接池按 thread_id 隔离，并发两个会话互不串台。后台任务要保存引用，否则可能被 GC。

## 8.1 上传与预览（阶段七补充）

### 接口
```
POST /api/upload    multipart：files + thread_id
  → {"files":[{"name","rel_path","size_mb","fps","frames","width","height","decodable"}]}
GET  /api/video?path=...   受控预览（只允许 UPLOAD_ROOT 内）
```

### 四层防护（缺一不可）
```python
name = Path(file.filename.replace("\\", "/")).name   # 1. 只取 basename
if Path(name).suffix.lower() not in ALLOWED_SUFFIX:  # 2. 后缀白名单
    raise HTTPException(400)
dest = (target_dir / name).resolve()                 # 3. resolve + 越界校验
if not dest.is_relative_to(UPLOAD_ROOT):
    raise HTTPException(400)
while chunk := await file.read(1024 * 1024):         # 4. 流式写入 + 超限删残
    ...
```

补充两条：
- 前端 `accept="video/*"` 只是体验，不是校验
- MIME 可伪造 → 用 OpenCV 真解码一次

### 失败要早
```python
meta = _probe_video(dest)          # 读一帧，拿 fps/frames/size
if not meta["decodable"]:
    dest.unlink(missing_ok=True)   # 不等 Agent 跑 40 秒才失败
    raise HTTPException(400, "无法解码")
```

### 静态文件坑
| 做法 | 结果 |
|---|---|
| `mount("/uploads", StaticFiles(...))` | 绕过校验，知道文件名就能下 |
| `GET /api/video` + `is_relative_to` | ✅ 受控 |

与原项目 `/output` 挂载是同一个教训，这次没再犯。

### 前端三件套
| 技术 | 原因 |
|---|---|
| `FormData` + `XMLHttpRequest` | `fetch` **不支持上传进度** |
| 拖拽 API | `dragover` 必须 `preventDefault()` |
| `crypto.randomUUID()` | 原生生成会话 ID |

上传成功后自动填路径：`q.value = f0.rel_path + ' 这段正手帮我看看'` —— 用户不该看到"路径"这种内部概念。

### 实测
```
上传 → 0.51MB / 30fps / 93帧 / 1920x1080 / decodable=true
非法 thread_id → 400
/api/video?path=/etc/passwd → 403
端到端 → dispatch 技术分析师 → 质量门禁拒答
```

### 面试 30 秒
> 上传做了四层防护：basename、后缀白名单、`resolve + is_relative_to`、流式写入加大小上限并清理残文件。上传后立刻用 OpenCV 读一帧探测可解码性，坏文件当场拒绝，避免用户等几十秒才看到失败。预览走受控接口而不是静态挂载。

### 常见追问
| 问题 | 答案 |
|---|---|
| 为什么不一次性 `await file.read()` | 200MB 会占满内存，分块才能边写边计数 |
| `Content-Length` 为什么不可靠 | 可伪造；分块传输时没有 |
| 视频预览为什么需要 Range | 拖动进度条要分段请求，`FileResponse` 已支持 |
| 上传目录会不会无限增长 | 会，需要按 thread_id + 时间做清理 |

## 9. 指标口径重修（横跨阶段 1~8 的一次纠错）

### 现象
同一段视频，击球次数在 7 / 14 / 2 之间跳，指标里出现物理上不可能的值：

```
wrist_speed      194.8      # 人挥不了这么快
contact_offset   +26.6      # 26 个体高，早飞出画面了
elbow_angle      27°~155°   # 同一段视频内极差 128°
```

### 根因：归一化尺度选错了
所有指标都除以「肩宽」。**侧面拍摄时两肩在 2D 上几乎重合，肩宽会塌缩到接近 0**：

| 尺度 | median | min | 变异系数 |
|---|---|---|---|
| 肩宽 | 0.0541 | **0.0009** | 0.57 |
| 躯干长 | 0.0896 | 0.0698 | 0.17 |
| 体高 | 0.1734 | 0.1547 | **0.05** |

除以一个接近 0 的数，腕速被放大 3~4 倍，凭空造出假峰。

### 修法
`scale = 体高（肩中点 → 脚踝）`；脚踝不可见时退化为 `1.9 × 躯干长`。
肩宽单独存 `shoulder_width`，只用于判断视角，不参与归一化。

### 连带修正
| 问题 | 原做法 | 改法 |
|---|---|---|
| 阈值拍脑袋 | 固定 75 分位 + 0.35s 间隔 | 相对静默基线：`base=p25`、`height=max(p75, 2.5×base)`、`prominence=1.5×base`、`gap=0.9s` |
| 肘角过滤误杀 | 下限 60° | 下限 45° |
| 肩角 ±180 跳变 | `np.unwrap` 解缠绕 | 侧面不可用时返回 `None`；可用时取相对水平的绝对倾角折到 `[0,90]` |
| 单样本伪装稳定 | std=0 → cv=0 | 样本 < 2 时 std / iqr / cv 全部 `None` |
| CV 爆炸 | 均值≈0 照算 | `abs(mean) < 0.3` 不报 CV |

### 结果
| | 修正前 | 修正后 |
|---|---|---|
| 击球次数 | 14 | **8**（与人工计数一致） |
| 腕速 | 33~202 | 9.1~11.2 |
| 击球点偏移 | 均值 +6.74，-9.7~+26.6 | 均值 +0.75，0.17~1.11 |
| 肘角 | 27°~155° | 116°~177° |

### 顺手做的对照实验：lite vs full
| | lite | full |
|---|---|---|
| 击球次数 | 8 | 6 |
| 腕速 CV | 0.072 | 0.171 |
| 肘角 CV | 0.132 | 0.347 |

**更强的模型反而更差**。full 逐帧求最优、抖动更大，而速度是对轨迹求导，噪声会被放大；lite 反而自带平滑。
结论：**瓶颈在 2D 投影和拍摄条件，不在骨干网络**。

### 三条教训
1. 归一化尺度必须选**视角不变**的量（体高 > 躯干长 > 肩宽）
2. CV 在均值接近 0 时没有意义（`backswing_height` 就属于这类）
3. 换更强模型之前，先确认误差来自哪一层

### 面试 30 秒
> 击球次数忽多忽少，我一开始去调阈值，越调越乱。后来发现根因是归一化尺度用错了：侧面拍摄时两肩在 2D 上重叠，肩宽塌缩到 0.0009，所有除以它的量都被放大。换成体高（变异 0.05）之后，次数从 14 回到人工计数的 8。顺手对比了 lite 和 full，更强的模型反而更差——说明瓶颈不在模型精度，在 2D 投影和拍摄距离。

## 10. 阶段八：跨会话记忆与纵向对比

### 为什么必须做
LangGraph 的 checkpoint 按 `thread_id` 隔离，**天然记得"这次对话"，但记不住"这个用户"**。
用户真正问的是"我练了一个月有没有进步"，这件事必须落到会话之外。

### 结构
```
写入：analyze_stroke ──▶ record_analysis ──▶ analyses 表（SQLite）
读取：get_progress ◀── build_progress（首次 vs 最近）◀── analyses 表
```
`thread_id` 由 runner 通过 `ContextVar` 注入，工具侧只读不写。

### 四个设计决定
| 决定 | 理由 |
|---|---|
| 用 SQLite 不用向量库 | 要的是"按时间取数 + 聚合"，一条 SQL 就够；向量检索解决的是"找相似内容" |
| `thread_id` 不让模型填 | 模型会编；由调用方注入才可靠 |
| 记忆不自动注入上下文 | 历史可能几十条，每问一次都塞进去是浪费；做成工具按需取 |
| 对比用首末而非回归 | 简单可解释，样本少时回归不稳 |

### 三道诚实性护栏
| 护栏 | 触发条件 | 行为 |
|---|---|---|
| `insufficient` | 可对比记录 < 2 | 只说"历史不足"，禁止编造趋势 |
| `usable_sessions` | 单次 < 2 次击球 | 算不出 std，不进趋势 |
| `setup_mismatch` | 体高差异 > 40% | 提示"不同机位不宜直接比较" |

### 抓到的两个坑
1. **主调度器不肯调度**：问"我有没有进步"，它回答"请把两份视频发我"——把"需要视频路径"的规则套上来了。
   修法：Prompt 加例外，"历史对比类问题不需要视频路径，直接调度"。
2. **子智能体偷偷重新分析历史视频**：把路径放进返回值后，它拿到路径就"顺手"重跑了一遍，**同一次训练记了 4 条账**。
   修法（两层）：返回值只给文件名（结构上让它跑不了）+ Prompt 明确禁止。

> 教训：**结构限制 > Prompt 约束**。先让错误路径走不通，再补话术。

### 另一个隐坑
`with sqlite3.connect(...)` 只提交事务，**不关闭连接**。改成 `with closing(_connect()) as conn, conn:`。

### 实测
```
空库      → 0 条记录，如实说"看不出有没有进步"
2 条记录  → 识别出"两次是同一条视频、时隔 11 秒"，拒绝给趋势
```

### 面试 30 秒
> 会话状态按 thread_id 隔离，做不到跨会话记忆，所以把每次分析落到 SQLite。为了让模型不能瞎编，加了三条护栏：记录不足就说不足、单次击球少于 2 次不进趋势、拍摄尺度差太多就提示不可比。中途还踩了一个坑——子智能体拿到历史视频路径后会自己重跑一遍，把同一次训练记成了 4 条，最后靠"只返回文件名"这种结构手段解决，而不是靠 Prompt。

## 11. 阶段九：训练计划

### 核心原则
**短板由代码判，模型只负责组织语言。**
让模型自己看 summary 决定练什么，它会挑解释起来顺手的指标；代码按 CV 排名后，它只能服从。

### 为什么按 CV 而不是绝对值
各指标量纲不同（偏移是体高倍数，肘角是度），绝对值不可比；但"自己跟自己的波动"可比。

### 四个分支
| 场景 | 行为 |
|---|---|
| 空库 | 报错："请先上传一段击球视频" |
| 有短板 | 取 CV 最大的 1~2 项，轮换排周计划 |
| 全部 CV < 0.15 | 不给加练，改维持性计划（每周 2 次） |
| `weeks` 越界 | 钳制到 1 / 12 |

### 实测输出（8 次击球那段）
```
ranking  击球点稳定性 0.375 → 随挥完整度 0.209 → 击球时肘角 0.132 → 挥拍速度 0.072
周 1 击球点稳定性 · 周 2 随挥完整度 · 周 3 击球点稳定性 · 周 4 随挥完整度
```

### 面试 30 秒
> 训练计划的关键不是让模型写计划，而是让代码决定练什么。模型看到一堆指标会挑自己讲得顺的，所以我先按变异系数排名，把"最不稳的是击球点"这个结论用代码钉死，模型只负责把它翻译成可执行的动作。指标到训练项的映射是经验设定，我在返回值里写明了未经教练校准。

## 12. 阶段十：知识检索

### 决策
| 项 | 选择 | 理由 |
|---|---|---|
| 引擎 | 自写 BM25（约 90 行） | 27 条语料用不着向量库；零依赖、离线可跑、打分可解释 |
| 分词 | 单字 + 二元组 | 不为一个词典引入 jieba |
| 打分 | **只用二元组及以上** | 单字太容易误命中，见下 |
| 置信度 | 用查询词**覆盖度**而非得分 | 得分受文档长度影响，覆盖度直接回答"问的词命中多少" |

### 语料
自建 27 条，覆盖正手 / 反手 / 发球 / 步伐 / 体能伤病 / 战术。
每条带 `metric` 字段指向 `analyze_stroke` 的指标（如 `fh_contact_point → contact_offset`），
这样"你击球点偏后"能直接接上"击球点应该在哪、为什么"。

### 抓到的坑
初版用单字参与打分，**"今天天气怎么样" 匹配到了 "每拍准备动作都不一样"**——只因为都含"样"字。
改成只看二元组（查询本身没有二元组时才退回单字）后：

```
hit@1 = 7/7（含一条无关查询应返回空）
```

这个冒烟测试写在 `knowledge.py` 的 `__main__` 里，改语料后直接跑就知道有没有退化。

### 面试 30 秒
> 知识库只有 27 条，我没上向量库，纯 Python 写了 BM25，中文按二元组切分。第一版用单字打分，结果"今天天气怎么样"匹配到了"每拍准备动作都不一样"，因为都有个"样"字；改成只用二元组打分后命中率到 7/7。置信度我用的是查询词覆盖度而不是检索得分，因为得分受文档长度影响，覆盖度更能说明"问题被回答了多少"。

## 13. 阶段十一：MCP 包装

### 做了什么
把 5 个工具暴露成 MCP 服务（stdio 传输），并验证了一条真正走协议的编排路径。

```
mcp_server.py    analyze_stroke / search_technique / get_progress /
                 make_training_plan / filter_rackets
mcp_agent.py     通过 stdio 客户端加载工具 → configure() 替换子智能体工具集
```

### 编排图不用改
子智能体的工具集做成可替换的注册表：

```python
SUBAGENTS = {}

def configure(stroke_tools=None, gear_tools=None):
    SUBAGENTS.clear()
    SUBAGENTS.update({... build_subagent(tools, ..., llm=...) ...})
```

同一张图，既能用进程内 `@tool`，也能用 MCP 客户端加载来的工具。工具换了，门禁、评测断言、上下文压缩全部复用。

### 三个真实的坑
| 坑 | 现象 | 修法 |
|---|---|---|
| SDK 版本漂移 | 装 `langchain-mcp-adapters` 把 `mcp` 从 2.3.0 降到 1.30.0；2.x 的 `MCPServer` 在 1.x 叫 `FastMCP`，直接 ImportError | 服务端 try/except 两版兼容 |
| content blocks | MCP 返回 `[{"type":"text","text":"{...json...}"}]`，而门禁 `evaluate()` 用 `json.loads(str(content))`。**不归一化会把所有结果判成 refuse——不报错，只表现成"什么都拒答"** | 包装层把 content blocks 拼回 JSON 字符串 |
| 工具纯异步 | 适配器工具的 `func=None`、只有 `coroutine`，同步 `ToolNode` 抛 `NotImplementedError: StructuredTool does not support sync invocation` | 包装层用 `asyncio.run(tool.ainvoke(...))` 桥接 |

第二条最值得记：**静默失效**比报错危险得多。

### stdout 就是协议通道
stdio 传输下 stdout 是 JSON-RPC 通道，而视频管线内部会 `print("[1/4] 姿态提取完成…")`——一行进度就把握手打断了。

```python
@contextlib.contextmanager
def _stdout_to_stderr():
    with contextlib.redirect_stdout(sys.stderr):
        yield
```

### 实测
```
[MCP] 已通过协议加载 5 个工具，耗时 2.5s
技术问答：调度=['技术分析师'] 工具=['search_technique']  22.8s
球拍推荐：调度=['装备顾问']   工具=['filter_rackets']     21.6s
```
每次工具调用会新起一个 server 进程（mediapipe 导入约 2.5s），所以比直连（约 14s）慢。

### 为什么没有全量迁移
判据：**这个工具会不会被别人用？会不会跑在别的进程 / 语言里？**

| 类型 | 例子 | 该不该上 MCP |
|---|---|---|
| 外部能力 | GitHub、数据库、别人的 agent | 该，接口本来就要标准化 |
| 自有业务逻辑 | `analyze_stroke`、`filter_rackets` | 不该，它就该是进程内函数 |

迁到 MCP 的代价：序列化边界、进程生命周期、40 秒长任务的超时，还要去掉现有的线程桥接。
收益：架构统一，功能一个不多。

结论：**MCP 作为对外入口保留，Web 服务继续直连。**

### 面试 30 秒
> 我把工具包成了 MCP server，也验证过协议路径能跑通。但 Web 服务我没迁——因为工具是自有业务逻辑，本来就该在进程内。迁过去要付出序列化边界、进程生命周期、长任务超时三项成本，收益只是架构统一，功能一个不多。我的判据是"这个工具会不会被别人用、会不会跑在别的进程里"，会才值得上协议。

## 14. 跨阶段的四条主线

### ① Tool call
```
schema 决定选不选、填不填对
返回结构决定上层能不能判断
错误信息决定能不能自愈
```

### ② Context engineering
```
分层（磁盘 vs 上下文）
压缩（异常 > 全量）
引用（路径 > 内容）
折叠（历史只留最近）
```

### ③ Harness
```
断言过程 → 覆盖"不该做" → 重复跑 → 固定成本
```

### ④ 记忆
```
会话内（checkpoint，按 thread_id 隔离）  ≠  跨会话（落库）
判断权归代码，表达权归模型
结构限制 > Prompt 约束
```

## 15. 已知局限（面试时主动说）

| 局限 | 说明 | 下一步 |
|---|---|---|
| 指标的**区分度**未经证实 | 击球次数已能与人工计数对上（8 次），但"好动作 vs 坏动作"能否区分仍无教练标注 | 拍同机位、近/远两段，对比 CV 是否随距离下降 |
| `pose_landmarker_full.task` 效果更差 | 同一段视频次数 6 vs 8，抖动更大 | 固定用 lite；需要更高精度时换 RTMPose |
| 未做 3D 姿态 | 单目 + 2D 投影，`contact_offset` 丢掉了朝向纵深的分量 | 明确不做，用 2D 相对指标 |
| 多 worker 不支持 | 连接池在进程内 | Redis Pub/Sub |
| 装备数据仅 8 款示例 | 非真实 catalogue | 扩到 30~50 款并核对参数 |
| 评测用例 16 条 | 已断言到工具级，但不评回答质量 | 扩到 30 条，加回答质量与降级路径断言 |
| 技术知识库自建 43 条 | 27 条技术 + 16 条规则；规则按通行 ITF 理解整理，未逐条核对原文 | 引入教练标注或教材来源 |
| MCP 只覆盖 CLI 路径 | Web 服务仍用进程内工具；且每次调用新起 server 进程（约 2.5s） | 真要统一需改成常驻会话 + 全异步 |
| 检索冒烟测试 13 条 | 只能说明没明显退化 | 扩到 30 条，加否定查询 |
| 指标→训练项映射为经验设定 | 未验证"练这个真的能改善那个" | 用教练评分校准 |
| 记忆无 `user_id`、无 schema 版本 | 多用户会串数据；改表没有迁移路径 | 加 `user_id` 与 `schema_version` |
